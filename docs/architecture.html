ami Architecture

An anti-doomscroll companion built in layers, so it can grow into a general desktop agent by adding pieces instead of rewriting them. Rules decide when to step in; the companion decides what to say and whether you get more time.

Phase 1 runtime: one heartbeat's journey

Where a general desktop agent plugs in

Every layer has one small contract. Adding a capability means writing one module against that contract and registering it; nothing upstream or downstream changes.

Phase 2: Mark LVII as the voice shell

Decisions to keep

Enforcement never depends on a shell

The extension is force-installed through browser policies and fails closed after the daily budget if the daemon is down. Jarvis, Hermes or anything else is optional on top.

Rules decide when, the LLM decides what

Triggers are deterministic and testable. The model is called a few times a day, only at intervention points.

Local first, cloud for conversation

Titles and classification stay on Ollama. Cloud chat receives short usage summaries, not raw browsing history.

Wayland stays

Browser sensing works without screen access. Xorg is a deliberate later switch only for screen control.

Upgrade path

  1. Mark LVII shell. Plugin and speak bridge; voice questions about your usage and spoken escalations.
  2. Desktop-wide focus sensor. A tiny GNOME Shell extension reports the focused app over D-Bus, which works on Wayland. Rules can then cover apps, not just sites.
  3. More rules. Focus blocks tied to your daily goals, bedtime wind-down, meeting prep from the calendar.
  4. More reach. An MCP server interface lets Hermes, Claude or other agents read the timeline and call actions; Telegram for check-ins away from the desk.
  5. Screen control. Only on the Xorg session: screen reading and click/type actions, gated behind confirmation.
